# Выдача контента

HTTP-контракт для воркеров, которым нужны готовые видео и фото по языку без
доступа к SFTP-каталогам. Сервис сам выбирает из стока подходящие файлы,
упаковывает их в zip и удаляет выданные медиа из `content/<ниша>/<язык>/`
вместе с текстовым sidecar фото.

## Адресация: General и Profile

Разрешённый адрес выдачи всегда содержит язык, профиль — необязательная часть
адреса. Есть два режима, и они не смешиваются:

- **General** — `{"language":"ru"}`: общий контент без профиля из ниши
  `general`; сюда попадают ролики из TikTok и другой общий контент. Язык здесь
  задаёт запрос, поэтому поле обязательно. General всегда отдаёт только видео.
- **Profile** — `{"profile":"dating/profile_1"}`: это `dating.ru` +
  `profile_1`. Идентификатор профиля уже содержит тему, поэтому выбираются
  только строки этого `profile_id` того же языка. Язык берётся из реестра
  профиля; передавать `language` не обязательно, но если он передан, он
  должен совпадать с языком профиля.
- `{"profile":"general"}` — явный синоним General, то же, что профиль не
  указан; профиля с таким именем в реестре нет, поэтому `language` обязателен.

Тип контента — измерение профиля, а не отдельный профиль: один профиль даёт и
видео, и фото. Поле `type` (`video` по умолчанию или `photo`) выбирает тип
стока и архива; `type=photo` без профиля отклоняется с `422`, потому что
General — только видео. Один архив содержит один тип.

General никогда не получает профильный сток, профильный запрос — General.
Явный `language`, не совпадающий с языком профиля, отклоняется с `422` без
путей и внутренних деталей. `query` — тема supplier-видео, допустима только
для видео без профиля. Новые виды контента встраиваются в эти же два режима,
третий не заводится.

Архив можно получить двумя способами:

- синхронный `POST /api/v1/content/deliveries` — zip отдаётся потоком, контракт
  YouTube Kit не меняется;
- асинхронный `POST /api/v1/content/deliveries/link` — архив собирается в фоне,
  заливается на Filebin, а на сервере на 24 часа остаётся sidecar со ссылкой.

## Синхронная выдача

```
POST /api/v1/content/deliveries
```

Тело запроса:

```json
{"language": "ru", "count": 1, "request_id": "3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10"}
```

Профильный запрос может не указывать язык — тогда он берётся из профиля:

```json
{
  "profile": "dating/profile_1",
  "type": "photo",
  "count": 5,
  "request_id": "3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10"
}
```

| Поле | Правило |
|---|---|
| `language` | для General обязательна; для Profile необязательна и берётся из профиля, а если передана — должна совпадать с языком профиля. Строка по regex `^[a-z]{2,3}$` |
| `profile` | необязателен; идентификатор профиля, `general` — синоним General |
| `type` | тип контента: `video` (по умолчанию) или `photo`; `photo` требует профиль |
| `count` | целое от 1 до 300 |
| `request_id` | UUID |
| `query` | необязательная тема General-видео, строка от 1 до 200 символов; с профилем и с `type=photo` запрещена |

Фактический максимум `count` задаёт runtime-конфиг:

```yaml
delivery:
  # Максимум видео в одном архиве ручной выдачи.
  max_count: 100
```

Допустимы значения 1–300. Если `count` больше `delivery.max_count` или 300,
API отвечает `422`. Конфиги без секции `delivery` получают `max_count: 100`
через merge с дефолтами.

Выбираются только видео, у которых название в таблице `titles` непустое после
отбрасывания пробелов. Файл без названия остаётся в стоке и будет выдан после
следующего запуска flow `titles`. Для фото название не нужно: текст поста
берётся из sidecar рядом с файлом, отсутствие текста — валидный пост.

Если `query` не передан, выбираются названные General-видео всех тем. Если
передан — только названные General-видео, у которых `videos.query` совпадает
точно, с учётом регистра. В профильном режиме и для фото `query` запрещён.

Сток распознаёт тип по суффиксу: `.mp4`, `.mov`, `.webm`, `.mkv` — видео;
`.jpg`, `.jpeg`, `.png`, `.webp` — фото. Остальные файлы в сток не попадают.
Рядом с фото лежит необязательный `<name>.json` с текстом:

```json
{"text": "Текст поста"}
```

Нет файла, пустой объект `{}` или пустой `text` — валидный пост без текста.
Битый JSON не индексируется: строка не попадает в сток, в лог пишется
warning с путём sidecar без его содержимого.

## Авторизация

Заголовок `Authorization: Bearer <CONTENT_FACTORY_DELIVERY_TOKEN>`.

- Токен не задан в окружении — `503`, выдача выключена.
- Токен неверный или заголовка нет — `401`.
- Токен не логируется и не попадает в ответы.

## Ответы синхронной выдачи

| Код | Когда | Тело |
|---|---|---|
| `200` | есть хотя бы один подходящий файл | `application/zip`, `Content-Disposition: attachment; filename="delivery-<request_id>.zip"` |
| `204` | в адресе нет подходящих файлов, в том числе нет таблицы `titles` или базы | пусто |
| `401` | нет заголовка или токен неверный | JSON с ошибкой |
| `422` | тело не прошло валидацию, General без `language`, `count` выше лимита, `type=photo` без профиля | JSON с ошибкой |
| `500` | не удалось собрать или записать zip | JSON с ошибкой |
| `503` | `CONTENT_FACTORY_DELIVERY_TOKEN` не задан | JSON с ошибкой |

Если подходящих файлов меньше, чем `count`, отдаются все имеющиеся.

## Ручная выдача ссылкой

```
POST /api/v1/content/deliveries/link
```

Тело — как у синхронного запроса. Ответ `202`:

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "language": "ru",
  "status": "building",
  "created_at": "2026-05-01T12:00:00Z",
  "expires_at": "2026-05-02T12:00:00Z",
  "size": 0,
  "files": 0,
  "url": null,
  "error": null
}
```

`language` в ответе — вычисленный язык адреса: у профильного запроса без
`language` это язык профиля. Дальше job запрашивается по этому языку.

Архив собирается существующим `deliver()` в фоне с тем же `type`, что и у
запроса. Исходные медиа и sidecar фото удаляются только после успешной записи
zip, как и в синхронном режиме.

```
GET /api/v1/content/deliveries/{language}/{request_id}
```

Возвращает те же поля и текущий статус:

| Статус | Значение |
|---|---|
| `building` | сборка или заливка ещё идёт |
| `ready` | архив залит, `url` — публичная ссылка Filebin |
| `ready_local` | заливка не удалась, zip остался локально, `url=null`, `error` объясняет причину |
| `empty` | в адресе не было подходящих файлов, zip не создавался, `files=0` |
| `failed` | сборка не удалась, `error` содержит причину |

Ошибки:

- `401/503` — как у остальных маршрутов выдачи;
- `404` — job неизвестен или его TTL истёк (sidecar удаляется);
- `409` — другая сборка уже идёт;
- `422` — тело невалидно, `count` больше `delivery.max_count` или
  `type=photo` без профиля;
- `500` — не удалось запустить сборку или сохранить её состояние.

Одновременно в процессе API выполняется только одна сборка. Повторный `POST`
с тем же `request_id` возвращает существующий статус и не списывает сток.
Пока идёт сборка, запрос с другим `request_id` получает `409`.

## Filebin

После успешной сборки zip заливается на:

```
POST https://filebin.net/cf-<request_id>/<request_id>.zip
Content-Type: application/zip
```

Тело — сырые байты архива. Бин и имя файла детерминированы от `request_id`,
поэтому повторная заливка того же job попадает в тот же бин и не создаёт
второй. Наружу возвращается:

```
https://filebin.net/cf-<request_id>/<request_id>.zip
```

Успех — только `201`. JSON ответа разбирать не обязательно, но если в нём есть
`file.filename`, имя должно совпасть с отправленным. Таймаут заливки — 300 с:
архив около 1 ГиБ при наблюдаемых ~15 МБ/с заливается примерно за 71 с.
Таймауты скачивания у поставщика не меняются.

- Архив больше 1 ГБ не заливается — job получает `ready_local`.
- Filebin недоступен, ответил `400`, `403`, `412`, `413`, `429`, `5xx` или
  любым кодом кроме `201`, не ответил вовремя — job получает `ready_local`,
  zip остаётся на диске, `error` содержит код ошибки.
- Ответ `201` с невалидным JSON — не ошибка: ссылка строится из бина и имени
  файла.
- После успешной заливки локальный zip удаляется.
- Полный URL Filebin не пишется в лог и не попадает в ответы, кроме поля `url`
  самого job и списка архивов.
- Ссылка Filebin публичная и обходит IP-allowlist. Хост хранит файл 6 дней, но
  API перестаёт отдавать архив через 24 ч (`CONTENT_FACTORY_DELIVERY_RETENTION_HOURS`).
  Прямое скачивание идёт через `302` на подписанный S3 URL; это осознанно:
  видео уже публичны, а наша ссылка живёт сутки.

## Sidecar

Состояние ручной выдачи хранится рядом с архивом:

```
app_data/archive/<language>/<request_id>.json
```

Пример:

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "language": "ru",
  "status": "ready",
  "created_at": "2026-05-01T12:00:00Z",
  "expires_at": "2026-05-02T12:00:00Z",
  "size": 303000000,
  "files": 100,
  "url": "https://filebin.net/cf-11111111-1111-4111-8111-111111111111/11111111-1111-4111-8111-111111111111.zip",
  "error": null
}
```

Путь строится только из языка `^[a-z]{2,3}$` и UUID. При старте API:

- просроченные sidecar и их локальные zip удаляются;
- sidecar со статусом `building`, оставшийся от прошлого процесса, помечается
  `failed`; повторный `POST` с тем же `request_id` собирает выдачу заново.

## Темы стока

```
GET /api/v1/content/topics?language=ru
```

Ответ — остаток видео по темам для одного языка; фото в разбивку не входят:

```json
{
  "language": "ru",
  "topics": [{"query": "заправка", "count": 3}],
  "unclassified": 2
}
```

`topics` содержит только темы с `count > 0` и отсортирован по `query`.
`unclassified` — файлы без строки в `downloads`/`videos` или с пустым
`videos.query`.

## Формат архива

Внутри zip — пары файлов с трёхзначным номером. Медиа сохраняет исходное
расширение, `NNN.json` — sidecar YouTube Kit. Один архив всегда содержит
только один тип: видео и фото в одном zip не смешиваются.

Архив видео:

```
001.mp4
001.json
```

Архив фото:

```
001.jpg
001.json
```

`NNN.json` для видео:

```json
{
  "type": "video",
  "language": "ru",
  "profile_id": null,
  "title": "Заголовок видео"
}
```

`NNN.json` для фото:

```json
{
  "type": "photo",
  "language": "ru",
  "profile_id": "dating/profile_1",
  "text": "Текст поста"
}
```

`type` — единственный тип архива: видео и фото в одном архиве не смешиваются.
`profile_id` — `null` для General. `made_for_kids` не пишется. Фото без текста
даёт `"text": ""`.

### Заголовок видео

`title` берётся из `titles.title` по SHA-256 имени файла. Название пишется в
sidecar как есть: при выдаче оно не обрезается и не нормализуется. Описание
TikTok, удаление хэштегов и fallback не используются.

Названия назначает flow `titles`; файл без названия остаётся в стоке и будет
выдан после следующего запуска flow.

### Текст фото

`text` берётся из `<name>.json` рядом с фото. Файл удаляется вместе с фото
после успешной записи архива; отсутствие sidecar при повторной синхронизации
не ошибка.

## Хранение и TTL

Локальный архив хранится в:

```
app_data/archive/<language>/<request_id>.zip
```

Исходные медиа и sidecar фото удаляются только после успешной записи zip. Если
удаление файла не удалось, ошибка логируется, а zip всё равно отдаётся.

TTL задаётся `CONTENT_FACTORY_DELIVERY_RETENTION_HOURS` (по умолчанию `24`,
минимум `1`). В асинхронном режиме тот же TTL записывается в `expires_at`
sidecar. Просроченный job или архив отвечает `404`, sidecar удаляется.

## Список и скачивание архивов

```
GET /api/v1/content/archives
```

Возвращает массив живых архивов, новые сверху. Локальные архивы без sidecar
по-прежнему видны как `storage=local`:

```json
[
  {
    "language": "ru",
    "request_id": "3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10",
    "size": 303000000,
    "created_at": "2026-05-01T12:00:00Z",
    "expires_at": "2026-05-02T12:00:00Z",
    "storage": "remote",
    "url": "https://filebin.net/cf-3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10/3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10.zip",
    "files": 100
  }
]
```

- `storage=remote` — архив на Filebin, `url` заполнен, `files` берётся из
  sidecar;
- `storage=local` — zip на диске, `url=null`;
- для старого локального архива без sidecar `files=null`, `size` — размер файла;
- `created_at`/`expires_at` берутся из sidecar, для старого архива — из mtime
  файла.

```
GET /api/v1/content/archives/{language}/{request_id}.zip
```

- для `storage=remote` — `302 Location: <url>` на Filebin;
- для локального архива — `FileResponse` (`application/zip`, имя
  `delivery-<request_id>.zip`) без повторной сборки и без изменения стока;
- если архива нет, он истёк или `ready_local` остался без zip — `404`.

## Идемпотентность

Ключ идемпотентности — `request_id` вместе с вычисленным языком адреса. Повтор
с тем же `request_id` в пределах TTL возвращает тот же файл архива или тот же
статус job и не трогает новые файлы в стоке. Если zip или sidecar старше TTL,
они удаляются, и выдача собирается заново с тем же `request_id`.

## Очистка

Очистку выполняет APScheduler в процессе API:

- `AsyncIOScheduler`, `CronTrigger(minute=0)` — раз в час;
- job id `delivery-archive-cleanup`, `max_instances=1`, `coalesce=True`;
- один прогон очистки и восстановления sidecar выполняется при старте API.

Планировщик не запускает Prefect flow и не требует воркера. Ошибки очистки
(нет прав, гонка при удалении) логируются и не роняют API.

## Примеры

Синхронная выдача:

```bash
curl -f -X POST http://127.0.0.1:8000/api/v1/content/deliveries \
  -H "Authorization: Bearer $CONTENT_FACTORY_DELIVERY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"language":"ru","count":2,"request_id":"3f1c1b0e-6f1a-4f6e-9d2e-0f6a7b8c9d10"}' \
  -o delivery.zip
```

Ручная выдача ссылкой:

```bash
curl -f -X POST http://127.0.0.1:8000/api/v1/content/deliveries/link \
  -H "Authorization: Bearer $CONTENT_FACTORY_DELIVERY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"language":"ru","count":100,"request_id":"11111111-1111-4111-8111-111111111111"}'

curl -f http://127.0.0.1:8000/api/v1/content/deliveries/ru/11111111-1111-4111-8111-111111111111 \
  -H "Authorization: Bearer $CONTENT_FACTORY_DELIVERY_TOKEN"
```

Проверка содержимого локального архива:

```bash
unzip -l delivery.zip
```

## Сеть

В compose API кроме сети `default` подключён к внутренней сети `content-bus`
с alias `content-factory-api`. Публичный порт остаётся только на loopback
(`127.0.0.1:8000:8000`). Каталог `archive/` создаёт `init` от root и отдаёт
пользователю `10001`; он находится вне SFTP-chroot `content/`.

## Граничные случаи

- Пустой или отсутствующий `content/<ниша>/<язык>/` (для General —
  `content/general/<язык>/`) — синхронно `204`, вручную `empty`.
- В одном языке есть и общий, и профильный сток — General отдаёт только
  `general` без профиля, Profile — только свой `profile_id`; выдача одного
  режима не трогает другой.
- `profile` чужого языка, `profile` вместе с `query`, отсутствие `language`
  без профиля (General), `type=photo` без профиля, `type=photo` с `query` —
  `422`.
- Есть видео, но ни одного названия — синхронно `204`, вручную `empty`;
  файлы остаются в стоке. Для фото название не требуется.
- Смешанный сток — выдаются только названные файлы, неназванные остаются.
- Меньше названных файлов, чем `count` — отдаются все.
- Нет базы, нет таблицы `titles` или база битая — названных файлов нет,
  синхронно `204`, вручную `empty`; файл базы не создаётся.
- Пустой `titles.title` или название только из пробелов — файл считается
  неназванным.
- Строка `titles` для уже выданного файла игнорируется, ошибки нет.
- Название добавлено после выбора источников — текущий запрос его не увидит,
  следующий увидит.
- Нет строки в `videos`/`downloads` — файл всё равно может быть назван и выдан;
  в `query` он не попадает.
- `query` задан, но совпадений среди названных нет — сток не меняется.
- Архив удалён между списком и скачиванием — `404`, не `500`.
- Ошибка сборки zip — `.tmp` удаляется, исходники остаются; синхронно `500`,
  job переходит в `failed`.
- Ошибка удаления исходника или sidecar фото после сборки — логируется, zip
  отдаётся.
- Фото без sidecar, с `{}` или с пустым `text` — валидный пост, в архиве
  `"text": ""`; sidecar удаляется вместе с фото.
- Битая JSON-строка sidecar фото — файл не индексируется, warning с путём
  sidecar без содержимого; другие файлы стока не затронуты.
- `name.mp4` и `name.jpg` в одной папке — разные строки стока; выборка по
  `type` берёт нужную.
- Старая база без колонки `content_type` — миграция помечает существующие
  строки как `video`; повторная индексация не нужна.
- Filebin недоступен или архив больше 1 ГБ — `ready_local`, zip остаётся.
- API перезапущен во время `building` — при старте job получает `failed`,
  повторный `POST` собирает заново.
- Два `POST` одновременно — один `202`, второй `409`; сток не списывается
  дважды.
- Старый локальный архив без sidecar — `storage=local`, как раньше.
- Sidecar `ready` с URL, но без zip — `storage=remote`; sidecar `ready_local`
  без zip — `404`.
- `language="ru/"`, `count=0`, `count=301`, не-UUID — `422`.
