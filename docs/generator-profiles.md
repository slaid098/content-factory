# Профили генератора: рецепт производства

`profile.yaml` описывает не только параметры рендера, но и то, каким
способом и с какими проверками производится контент. Блок `production`
необязателен; его отсутствие означает прежний единственный слой Vast.

```yaml
production:
  - producer: vast
    type: video
    qa: [media, clef]
```

Рецепт фото-профиля:

```yaml
production:
  - producer: card
    type: photo
    qa: [image]
```

Профиль может объявить несколько независимых цепочек: каждый шаг становится
корневым слоем `Layer(name=producer, producer=producer, inputs=(),
output=type, checks=qa)`. Например, видео и фото одной карточки:

```yaml
production:
  - producer: vast
    type: video
    qa: [media, clef]
  - producer: card
    type: photo
    qa: [image]
```

Оба слоя выполняются в одном прогоне конвейера с одним `run_id`; это не
последовательность «сначала видео, потом фото», а две независимые ветки.

Поля шага:

- `producer` — имя зарегистрированного producer'а, обязательно;
- `type` — тип контента, по умолчанию `video`; producer должен его
  поддерживать (`vast` производит только видео, `card` — только фото);
- `qa` — упорядоченный список именованных проверок слоя. По умолчанию он
  зависит от типа: для `video` — `[media, clef]`, для `photo` — `[image]`.
  Пустой список запрещён: рецепт не может отключать QA целиком. Проверки
  другого типа запрещены при загрузке: `media`/`clef` в photo-шаге и `image`
  в video-шаге дают `ProfileError`.

Без блока `production` профиль получает ровно текущее поведение:

```yaml
production:
  - producer: vast
    type: video
    qa: [media, clef]
```

Старые `profile.yaml` без блока не мигрируются.

## Проверки при загрузке

`load_profile` проверяет рецепт до аренды сервера и бросает `ProfileError`,
если:

- `production` пуст или задан не списком;
- шаг не словарь или в нём нет `producer`;
- producer или QA не зарегистрированы (в сообщении есть имя профиля и
  список допустимых значений);
- producer повторяется в рецепте, QA повторяется в шаге;
- `type` неизвестен или не поддерживается producer'ом;
- QA не подходит типу шага (`media`/`clef` для `photo`, `image` для
  `video`).

## Producers

Реестр — `services/production/registry.py`: `register(name, factory)`,
`resolve(name)`, `available()`. Встроенные producers — `vast` и `card`.
Тесты используют отдельный `ProducerRegistry` или `reset()`, поэтому
инъекция не протекает в другие тесты.

Производители:

- `vast` — слой поверх существующего `services.generator.generate_batch`,
  `supported_outputs = {video}`. На один прогон группы вызывается ровно один
  `generate_batch` со всеми именами профилей группы; он арендует серверы,
  генерирует видео, публикует их в сток и возвращает отчёт, из которого
  producer берёт артефакты слоя.
- `card` — фото-пост из текста профиля и отрендеренной карточки,
  `supported_outputs = {photo}`. Для каждого item берётся текст той же
  текстовой моделью, что и для видео, рисуется карточка поверх непрозрачного
  `text_bg_color` и сохраняется JPEG размера профиля (quality 90). В
  `generated/<language>/<profile_slug>/<run_id>/final/` лежат
  `<slug>_<run_id>_<NNN>.jpg` и sidecar `<slug>_<run_id>_<NNN>.json` с
  `{"text": caption}`, где caption — все строки всех блоков через `\n`.
  Пара публикуется в `content/<niche>/<language>/` жёсткой ссылкой, при
  невозможности — копией; при ошибке не остаётся ни `.jpg`, ни `.json`.
  Ошибка одного item не мешает остальным item'ам и профилям группы.

`flows/generate_batch/flow.py` загружает профили, проверяет `count`, берёт
блокировку и группирует профили по точной сигнатуре слоёв (имя, producer,
входы, выход, проверки). Группа получает свой `run_id` и один вызов
`run_pipeline`; отчёт `run.json` каждого профиля flow пишет один раз по
результату конвейера. Имя flow, параметры `profiles/count/dry_run` и строка
исхода сохраняются.

## Партии и `run_id`

Порядок групп — порядок первого профиля с таким рецептом, профили внутри
группы сохраняют порядок запроса. Одинаковые рецепты попадают в одну группу:
у них общий `run_id`, одна партия и один `run_pipeline`. Разные рецепты
получают разные `run_id`; все они перечисляются в строке исхода
(`run=... run=...`), ни одна партия не теряется. `count` проверяется до
первого producer'а и до аренды сервера. `run_id` обязан совпадать с шаблоном
`YYYYMMDDTHHMMSSZ[-N]`, а собранный каталог прогона проверяется на выход за
пределы `generated/<язык>/<профиль>/`. Профили, у которых совпадают язык и
`profile_slug` (например, `dating/p1` и `dating_p1`), отклоняются с
`ProfileError` до запуска producers: иначе они разделили бы один `run_dir` и
перезаписали бы файлы и отчёты друг друга.

## QA

В конвейере `qa` слоя — это `LayerCheck`-адаптеры над прежними проверками:

- `media` (`final`) — `qa.check_video`: mp4 читается, содержит видео,
  ожидаемую аудиодорожку и длительность в допуске;
- `clef` (`source`) — кадры исходника; их проверяет сам генератор до
  наложения текста, поэтому адаптер слоя только пропускает уже собранный
  источник;
- `image` (`final`) — PIL открывает готовый JPEG, файл непустой, а размеры
  совпадают с профилем.

Обязательные проверки producers не снимаются рецептом: `generate_batch`
всегда проверяет mp4 перед публикацией в сток, `card` всегда проверяет JPEG.
Слой `qa` проверяет уже готовый артефакт; producers публикуют только после
своих обязательных проверок, поэтому отклонённый item в сток не попадает и
в следующие слои не проходит. Причина провала попадает в `run.json`.

## `run.json`

Отчёт фиксирует рецепт и итог конвейера:

- `production` — слои профиля (`producer`, `type`, `qa`);
- у каждого item — `producer`, `type` и `qa` слоя;
- у фото-item `look_id`, `seed` и `frames` — `null`; у видео они
  заполнены;
- item, отклонённый проверкой слоя, остаётся в отчёте со статусом `failed`
  и причиной;
- `totals` считает принятые артефакты всех слоёв профиля.

При `dry_run` вызывается только `plan_layer` каждого слоя: video — план
looks/seeds/frames, photo — имена файлов и статус `dry_run`. `produce_layer`,
проверки, LLM, сеть и Vast не вызываются, курсор не двигается. Рецепт
проверяется и попадает в `run.json`.

## Название и пояснение профиля

В `profile.yaml` можно указать необязательные верхнеуровневые поля:

```yaml
title: Знакомства для 30+
summary: Спокойные знакомства с акцентом на серьёзные отношения.
```

`title` — одна строка длиной 3..80 символов, `summary` — одна строка длиной
20..300 символов. Реестр и `GET /api/v1/content/profiles` отдают `null`, если
поля нет или оно пустое; невалидный тип или длина пропускают профиль, как
битый YAML. Поля не влияют на генерацию, выдачу и refill.

Ручной flow `profiles_describe` (`prefect deployment`, без расписания)
обходит реестр и заполняет только профили, у которых `title` или `summary`
пусты. Для каждого вызывает текстовую модель `GENERATOR_MODEL` один раз;
промпт собирается из `profile.yaml`, `prompt_template.txt` (или старого
`video_prompt.txt`) и `text_prompt.txt`, ответ — строгий JSON с обоими
полями на языке профиля. Невалидный ответ повторяется один раз, затем
профиль попадает в `failed`, а файл остаётся прежним. Ошибка одного профиля
не останавливает остальные; без `OPENAI_API_KEY` flow выходит со статусом
`disabled`. Запись атомарная: `profile.yaml` перезаписывается через временный
файл с сохранением прав, остальные ключи остаются, комментарии не
сохраняются.
