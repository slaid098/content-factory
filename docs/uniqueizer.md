# Уникализация: очередь источников и буфер копий

CF не уникализирует видео сам и не знает, что делает движок внутри. Его
задача — вести метаданные исходников, хранить курсор профиля и держать в
буфере несколько готовых копий вперёд. Всё преобразование видео выполняет
внешний движок через порт `UniqueizerEngine.uniqueize(source, target)`.

## Каталоги

```
app_data/
  sources/<language>/<profile_slug>/          # исходники профиля
  unique/<language>/<profile_slug>/buffer/    # готовые копии
```

`<profile_slug>` — id профиля с заменой `/` на `_`: `dating/profile_1` →
`dating_profile_1`. Язык и id проверяются до построения пути. Слаг обязан
принадлежать ровно одному профилю реестра: если его делят
`dating/profile_1` и `dating_profile/1` или он принадлежит другому профилю,
импорт и очередь отклоняют id с `ValueError`.

В базе хранятся только метаданные; сами видео остаются на диске. Путь в
`source_items.path` записан относительно `data_dir` в POSIX-форме, поэтому
база переносится между хостами вместе с каталогом данных. Абсолютные пути,
`..`, `.`, обратные слэши и буквы диска отклоняются и в репозитории, и при
чтении очереди.

## Импорт источников

Импорт читает один профиль, зарегистрированный в `profiles/`:

```python
from pathlib import Path

from content_factory.services.uniqueizer import import_profile

result = import_profile(Path("app_data"), "ru", "dating/profile_1")
```

Для каждого файла импортёр:

1. вызывает `media.probe` (ffprobe) и получает длительность;
2. считает SHA-256 и размер;
3. пишет строку в `source_items` или обновляет существующую.

Файл без видео-потока, битый или нечитаемый пропускается с предупреждением и
не попадает в очередь. Повторный проход идемпотентен: тот же путь с тем же
содержимым даёт `unchanged`, изменившееся содержимое обновляет SHA-256 и
сбрасывает `used_at`/`use_count`, пропавший файл получает `missing_at`, а
вернувшийся — теряет эту метку. Дубликат по
`(language, profile_id, sha256)` оставляет одну строку: второй путь
пропускается как `duplicate`. Если тот же путь уже записан за другим языком
или профилем, строка не меняется и импорт считает это `conflict`.

Пакетный импорт сканирует `sources/<language>/<profile_slug>/` для профилей,
известных реестру, и печатает счётчики по каждому профилю:

```bash
python -m content_factory.services.uniqueizer.main --data-dir app_data
```

Пример строки:

```
ru dating/profile_1: добавлено 5, обновлено 0, без изменений 45,
вернулось 0, дубликатов 0, конфликтов 0, пропущено 0, пропало 0
```

Каталог неизвестного профиля или не-языковой каталог пропускается с
предупреждением: очереди нужен настоящий `profile_id`, а не догадка из имени
папки.

## Очередь и буфер

```python
from pathlib import Path

from content_factory.services.uniqueizer import UniqueizerQueue

result = UniqueizerQueue().refill(
    language="ru",
    profile_id="dating/profile_1",
    target=5,
    data_dir=Path("app_data"),
    engine=my_engine,  # реализует UniqueizerEngine
)
```

`refill`:

- требует `target > 0` и зарегистрированный профиль с однозначным слагом;
- считает готовые файлы в `buffer/`;
- пока готовых меньше `target`, берёт следующий исходник после курсора по
  лексикографическому порядку `path`, пропуская `missing_at IS NOT NULL`;
- проверяет, что путь из базы относительный, лежит внутри
  `sources/<language>/<profile_slug>/` и не проходит через симлинки; иначе
  движок не вызывается, а строка получает `missing_at`;
- вызывает `engine.uniqueize(source, target)`;
- проверяет, что движок создал непустой обычный файл;
- записывает `used_at`, увеличивает `use_count`, двигает курсор.

Один исходник даёт одну копию за проход. Имя копии детерминированное:
`<source_stem>_<copy_index:03d>.mp4`, где `copy_index = use_count + 1`.
Поэтому повторный `refill` не дублирует уже использованный исходник, а
следующая копия того же исходника (после изменения содержимого) получает
следующий номер.

`RefillResult` содержит:

| Поле | Значение |
|---|---|
| `created` | сколько копий создано за этот проход |
| `ready` | сколько готовых файлов в буфере после прохода |
| `exhausted` | исходники закончились, новых копий не будет |
| `failures` | кортеж `RefillFailure(source, reason)` |

При ошибке движка проход останавливается: частичный `target` удаляется,
курсор остаётся на последнем успешном исходнике, предыдущие копии не
трогаются. Если `target` уже существует, движок не вызывается и копия не
перезаписывается — это тоже `failure`. Пустой файл считается ошибкой.

После последнего исходника `refill` возвращает `exhausted=True`; повторный
вызов не зацикливается и не создаёт копий. Пустой буфер при пустом каталоге
источников — не ошибка.

## Порт движка

```python
from pathlib import Path


class MyEngine:
    def uniqueize(self, source: Path, target: Path) -> None:
        """Создать уникализированную копию source в target."""
```

Контракт один: движок создаёт непустой файл по `target` и не меняет
`source`. CF не проверяет содержимое копии, не накладывает текст, музыку,
эффекты и не запускает QA — это ответственность движка.

## База

Миграция `0002_sources` добавляет две таблицы:

- `source_items` — путь, язык, профиль, SHA-256, размер, длительность,
  `added_at`, `used_at`, `missing_at`, `use_count`;
- `source_cursors` — `language`, `profile_id`, `last_path`, `updated_at`,
  первичный ключ `(language, profile_id)`.

Уникальность `(language, profile_id, sha256)` не даёт одному профилю дважды
взять одно и то же видео. Курсор хранит последний успешно обработанный
`path`, а не числовой id, поэтому вставка источника в середину пути не
ломает порядок.

Запросы идут через `db.connection` с плейсхолдерами `?`; SQLite и PostgreSQL
дают одинаковое поведение. Порядок очереди — байтовый порядок `path`
(`COLLATE "C"` в PostgreSQL), совпадающий с сортировкой Python.
